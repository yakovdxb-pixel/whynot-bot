# HANDOFF — WHY NOT? OS

Перенос проекта на новый Mac. Собрано Claude Code 2026-10-01.

## 1. Что это за проект

**WHY NOT? OS** — внутренняя система для SMM-агентства WHY NOT?: Telegram-бот
`@whynotagencybot` + Telegram Mini App (веб-интерфейс внутри Telegram).
Заменяет ручное ведение контент-плана/задач в чатах на единую систему:
клиенты и проекты, контент-план (посты/сторис/рилсы), задачи с исполнителями
и дедлайнами, производственные джобы (съёмка/дизайн/монтаж), приём файлов
от исполнителей прямо в Telegram-топиках, идеи, съёмки, команда с ролями,
дашборд. Весь интерфейс — на русском (+ частично uz/en).

Живой прод: https://worker-production-7137.up.railway.app/webapp

## 2. Стек

- **Backend**: Python 3.11 (Railway) / локально протестировано на 3.13 —
  FastAPI + python-telegram-bot 21.3 (`[job-queue]` extra) + SQLAlchemy 2.0
  async + asyncpg.
- **DB**: PostgreSQL 18 (Railway, сервис `postgres-v2`, с volume).
  Схема — чистый SQLAlchemy `Base.metadata.create_all()` при старте
  + список идемпотентных `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` в
  `db/models.py::_MIGRATIONS` (никакого Alembic).
- **Frontend**: один файл `webapp/index.html` — ванильный JS SPA (без
  сборки, без npm, без фреймворков), Telegram Mini App SDK
  (`telegram-web-app.js` с CDN), service worker `webapp/sw.js` для
  офлайн-кэша оболочки приложения.
- **Deploy**: Railway, автодеплой на `git push` в `main`. `Procfile`:
  `web: python main.py`. `main.py` — единственная точка входа: сам держит
  polling бота в главном потоке + поднимает `uvicorn api:app` отдельным
  сабпроцессом (чтобы uvloop от uvicorn не конфликтовал с event loop бота).
- **Бот**: long polling (НЕ webhook — `webhook_set` всегда `false`,
  так и задумано). `drop_pending_updates=True` при старте.

## 3. Структура репозитория

```
main.py          — точка входа Railway (Procfile). Поднимает bot.py (polling,
                    главный поток) + uvicorn-сабпроцесс с api.py.
api.py           — FastAPI app: отдаёт webapp/ и sw.js, /health,
                    /api/bot-status (только с X-Admin-Secret), подключает
                    routes_whynot.router. Легаси sqlite-API удалён (2026-10).
routes_whynot.py — вся актуальная REST API ("WHY NOT? OS"): клиенты,
                    проекты, контент-план, задачи, съёмки, идеи, блокеры,
                    команда, референсы, дашборд. Это самый большой и самый
                    живой файл.
bot.py           — Telegram-бот, только Postgres: /start, /install, /bind,
                    /unbind, приём файлов из тем, реакция ✍ → референс (также 🏆 📌 📎 ⭐ ✅),
                    просрочки. Старый sqlite-бот удалён (2026-10). Бот должен
                    быть АДМИНОМ группы, иначе (privacy mode) не видит фото,
                    файлы и реакции — только команды.
db/models.py     — SQLAlchemy-модели + engine + _MIGRATIONS + init_db().
webapp/index.html — весь Mini App: разметка, стили, вся JS-логика одним
                    файлом. webapp/sw.js — service worker.
scripts/         — разовые утилиты (очистка тестовых данных, генерация иконок).
```

## 4. Что уже сделано

Система полностью рабочая и в проде, агентство ей реально пользуется.
Реализовано (в хронологии, самое важное):
- Клиенты/проекты (1 клиент ≈ 1 проект), назначение AM, бриф компании
  (цели/аудитория/тон оф войс/конкуренты), месячный план публикаций.
- Контент-план: тема/формат/вид контента/хук/сценарий/подпись, статусы
  публикации (в процессе → на одобрении → готов → опубликовано, +правка),
  референсы (ссылки и файлы).
- Задачи: приоритет, дедлайн, несколько исполнителей, статусы с историей
  (таймлайн с длительностью каждого этапа), просрочки (напоминание через
  15 мин), удаление.
- **Джобы из контент-плана**: кнопка «→ В задачи» на карточке контента
  одним нажатием создаёт 3 задачи (Съёмка/Дизайн/Монтаж, без исполнителя)
  — назначение исполнителя/дедлайна происходит уже в разделе «Главная»,
  обычной формой редактирования задачи. Задача пропадает с карточки
  контента, как только её взяли в работу (не дублируется).
- **Приём файлов через Telegram-топики**: тема супергруппы привязывается
  к проекту командой `/bind` (или `/bind Название` — создаёт клиента+проект
  и сразу привязывает). Исполнитель скидывает фото/видео/документ в
  привязанную тему → бот спрашивает, к какой активной задаче это относится
  → статус задачи → «на проверке», менеджер видит файл и жмёт
  Принять/На доработку/Опубликовать в приложении.
- Команда: роли (admin/am/director/editor/designer/videographer/
  mobilographer/driver/intern), доступ только для зарегистрированных
  (по `telegram_id`), закрытый экран для остальных.
- Съёмки, идеи (с голосованием), блокеры — с удалением.
- PWA: иконка на главный экран, service worker, десктопный режим окна
  (не на весь экран) для Telegram Desktop.
- Дашборд: план публикаций по проектам, разбивка по этапам пайплайна.

### Последнее, над чем работали (сессия до 2026-10-01)
Серия точечных UX-правок по итогам реального использования: сортировка
готовых задач вниз списка, показ «кто поставил задачу» (не только

## 5. Как запустить локально (пошагово)

Полноценный локальный запуск **не тестировался** в ходе разработки — всё
проверялось либо прямо в проде (после `git push`), либо фронтенд через
статик-сервер против прод-API. Ниже — что должно сработать по коду.

### Только фронтенд (без бэкенда, для правки вёрстки/JS)
```bash
cd webapp
python3 -m http.server 5173
# открыть http://localhost:5173 — API-запросы будут падать 404/CORS,
# но структура/стили/JS-логика без сети проверяются
```

### Полный бэкенд локально
```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# Нужна Postgres-база (локальная или туннель к Railway — см. ниже) и токен бота
export DATABASE_URL="postgresql+asyncpg://user:pass@localhost:5432/whynot_os"
export BOT_TOKEN="<токен ТЕСТОВОГО бота, НЕ прод-бота>"
export WEBAPP_URL="http://localhost:8000/webapp"
export PORT=8000

python main.py
# поднимет и polling бота, и uvicorn на :8000 разом
```
**Важно:** `main.py` жёстко ставит `RUN_BOT=0` сам себе и запускает бота
в своём потоке — не пытаться одновременно гонять `api.py` отдельно с
`RUN_BOT=1`, будет 409-конфликт с Telegram (два polling на один токен).
Для локальной разработки настоятельно завести **отдельного тестового
бота** через @BotFather, чтобы не конфликтовать с живым `@whynotagencybot`
и не слать уведомления реальным сотрудникам.

Доступ к `postgres.railway.internal` снаружи Railway не работает — это
внутренний DNS Railway. Для локальной БД либо поднять свою Postgres
(`brew install postgresql` / Docker), либо прокинуть публичный
connection string из Railway (Settings → Postgres service → Connect,
там есть внешний хост/порт).

### Тестовый бот локально
`@whynot_test_yakov_bot`, токен только в `.env.test` (в .gitignore, не в
Railway). Тестовая база — pgserver (Postgres 16) в
`~/.local/share/whynot-testdb/pgdata`, база `whynot_test`. Запуск:
```bash
set -a && . ./.env.test && set +a && .venv/bin/python bot.py
```
Если pgserver не запущен (после перезагрузки Mac):
`~/.local/share/whynot-testdb/.venv/bin/python -c "import pgserver; pgserver.get_server('$HOME/.local/share/whynot-testdb/pgdata', cleanup_mode=None)"`.
Тестовая группа «whynot test» с темами, бот в ней админ.

## 8. Переменные окружения (только имена)

Заданы на Railway → Service `worker` → Variables.

| Переменная | За что отвечает |
|---|---|
| `BOT_TOKEN` | токен Telegram-бота `@whynotagencybot` (от @BotFather) |
| `DATABASE_URL` | строка подключения к Postgres — **единственный источник адреса и пароля базы**. В коде дефолта нет: без переменной приложение падает при старте с `DATABASE_URL is not set`. У worker это ссылка `${{postgres-v2.DATABASE_URL}}` — при смене пароля обновится сама |
| `ADMIN_SECRET` | секрет для админ-эндпоинта `PATCH /api/users/{telegram_id}/role` (заголовок `X-Admin-Secret`) |
| `WEBAPP_URL` | публичный URL Mini App, используется ботом для кнопок «Открыть приложение» |
| `RUN_BOT` | `0`/`1` — чтобы бот не поднимался дважды; `main.py` всегда сам ставит `0` перед запуском, трогать не нужно |
| `PORT` | порт для uvicorn, подставляет сам Railway |

Секретных `.env`-файлов в репозитории и на этой машине нет — все значения
только в Railway. Локально `DATABASE_URL` задаётся в `.claude/launch.json`
(конфиг `api-local`) или через `export`.

## 9. Важные решения и договорённости (не видны из кода)

- **1 клиент ≈ 1 проект.** Изначально система поддерживала несколько
  проектов на клиента (напр. отдельно Instagram/TikTok), но по факту это
  никогда не использовалось и путало — кнопку «Ещё проект» убрали. Модель
  данных технически всё ещё позволяет много проектов на клиента, просто
  UI больше не даёт это создать штатно.
- **Роли — просто текст в Python, не enum в Postgres.** И `users.role`,
  и `tasks.status` изначально были Postgres ENUM, потом намеренно
  переведены на `TEXT` + валидация набором значений в Python
  (`USER_ROLES`, `TASK_STATUSES` в `routes_whynot.py`) — добавлять новое
  значение статуса/роли значит просто дописать строку в Python-set,
  миграция не нужна. Если видишь `ALTER TABLE ... TYPE TEXT USING ...::text`
  в `_MIGRATIONS` — это тот самый переход, только dev не переводи обратно.
- **Задача vs контент — разные сущности, специально.** Контент-план
  (`ContentItem`) — это планирование (тема, формат, дата публикации).
  Исполнение (кто снимает/монтирует/дизайнит) — это обычные `Task` со
  спецполем `job_kind` (`shoot`/`design`/`edit`) и `content_id`,
  назначаются и трекаются как любые другие задачи в «Главной». Так сделано
  специально после жалобы, что в контент-плане было «бессмысленно»
  назначать исполнителей отдельно от общего пайплайна задач.
- **Привязка Telegram-темы к проекту — только через `/bind`.** Раньше
  обсуждалась идея хранить `telegram_topic_id` прямо на клиенте — от неё
  отказались в пользу уже существующей таблицы `project_chats`
  (заполняется командой `/bind` в супергруппе), чтобы не было двух
  параллельных источников правды о привязке темы.
- **Уведомления — лучшее из возможного, без гарантии доставки.**
  `_tg_send()` в `routes_whynot.py` — «fire and forget», ошибки только
  пишутся в лог Railway, ни отправитель, ни получатель не видят, что
  сообщение не дошло. Самая частая причина «не пришло уведомление» —
  человек никогда не нажимал Start в личке с ботом (Telegram не даёт боту
  написать первым).
- **`/tmp` на машине разработки периодически чистится системой** (файлы
  старше ~3 дней), из-за чего рабочий git-клон и SSH deploy-ключ несколько
  раз терялись за время разработки. Из-за этого в истории коммитов
  встречаются повторные генерации deploy-ключей — это не инцидент
  безопасности, просто особенность машины. На новом Mac, если клон будет
  жить не в `/tmp`, а в постоянной папке, эта проблема уйдёт сама собой.
- **Публичный репозиторий — осознанный выбор** (упрощает клонирование без
  ключей), поэтому никаких секретов в коде — только в переменных Railway.
  Старый пароль БД навсегда остался в git-истории, поэтому его сменили
  (см. раздел 10), а не стали переписывать историю.

## 10. База данных: пароль и хранение (важно)

### Пароль — решено (октябрь 2026)
Раньше в `db/models.py` и `scripts/cleanup_db.py` был захардкожен дефолтный
`DATABASE_URL` с логином/паролем, а репозиторий публичный. Сделано:
- Пароль пользователя `whynot` сменён в самой базе (Console сервиса
  `postgres` в Railway → `\password`). Старый пароль из git-истории больше
  не работает.
- У сервиса `worker` обновлён `DATABASE_URL`, worker передеплоен,
  `/health` → `{"db":"ok"}`.
- Дефолт из кода убран (коммит `061f1d8`): `DATABASE_URL` берётся только
  из окружения, без него приложение не стартует.
- Старый пароль/`POSTGRES_PASSWORD` старого сервиса больше не важны:
  прод переехал на `postgres-v2` (см. ниже).

### Postgres без volume → переезд на postgres-v2
Сервис `postgres` в Railway — обычный docker-контейнер, и на схеме
проекта у него **не видно volume** (volume виден только у `worker`). Если
данные Postgres (`PGDATA`) лежат внутри контейнера, а не на volume, то
любой рестарт/редеплой сервиса `postgres` (в том числе из-за изменения
его переменных) может стереть всю боевую базу.

**Проверено 2026-10-03:** `PGDATA=/var/lib/postgresql/data/pgdata` на
файловой системе `overlay` — volume у старого `postgres` (образ `postgres:16`)
действительно нет. Volume `worker-volume` (`/data`) принадлежит worker, к базе
отношения не имеет.

**Переезд выполнен 2026-10-03 19:50 (UTC+5):** прод работает на сервисе
`postgres-v2` (шаблон Railway `postgres-ssl:18`, volume `postgres-volume` в
`/var/lib/postgresql/data`, база `railway`, пользователь `postgres`, без TCP
Proxy). У worker `DATABASE_URL` = `${{postgres-v2.DATABASE_URL}}` — ссылка,
при смене пароля обновится сама. Перед переключением залит свежий дамп
(22 таблицы совпали по числу строк, последовательности в порядке), копия
лежит на Mac в `why not os/backup_whynot_20261003_1948_cutover.sql.gz`.
Старый `postgres` (без volume) оставлен как запасной, с ним не работают —
удалить через 1–2 недели. Откат: вернуть у worker прежнюю строку
`postgresql://whynot:<пароль>@postgres.railway.internal:5432/whynot_os`
(данные, внесённые после 19:50, в старой базе отсутствуют).

**Ежедневный бэкап (с 2026-10-03):** на Mac владельца launchd-задача
`~/Library/LaunchAgents/com.whynot.db-backup.plist` каждый день в 14:00
(если Mac спал — при пробуждении) запускает `~/.local/share/whynot-backup/backup.sh`:
`pg_dump` из `postgres-v2` через `railway ssh` → `~/WhyNot-backups/whynot_*.sql.gz`,
хранятся последние 30, журнал в `~/WhyNot-backups/backup.log`, при ошибке —
уведомление macOS. Если выключенный Mac — бэкапа в этот день нет. Встроенные
бэкапы volume Railway на тарифе Hobby через API недоступны («Not Authorized»).

**Как снимать/заливать дампы без psql на Mac** (через `railway ssh`, SSH-ключ
`~/.ssh/id_ed25519` зарегистрирован в Railway):
```bash
# бэкап боевой базы на Mac
railway ssh -s postgres-v2 -- sh -c 'pg_dump -U "$PGUSER" -d "$PGDATABASE"' | gzip > backup_$(date +%Y%m%d_%H%M).sql.gz
# заливка дампа (в ПУСТУЮ базу; одной транзакцией)
gzip -dc backup.sql.gz | railway ssh -s postgres-v2 -- sh -c 'psql -q -v ON_ERROR_STOP=1 --single-transaction -U "$PGUSER" -d "$PGDATABASE"'
```

Правило: старый `postgres` до удаления не перезапускать и не менять — его
данные лежат в контейнере и пропадут при рестарте (это нужно только для
отката, прод от него не зависит).
