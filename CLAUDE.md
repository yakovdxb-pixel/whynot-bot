# CLAUDE.md

Контекст для Claude Code в этом репозитории. Для полной картины (что
сделано, TODO, внешние сервисы, переменные окружения) см. `HANDOFF.md` в

## Что это

WHY NOT? OS — Telegram-бот (`@whynotagencybot`) + Telegram Mini App для
SMM-агентства. Продакшен на Railway, автодеплой на `git push` в `main`.
Прод: https://worker-production-7137.up.railway.app/webapp

## Стек и структура

Python (FastAPI + python-telegram-bot + SQLAlchemy async/asyncpg) на
бэкенде, один файл `webapp/index.html` (ванильный JS, без сборки) на
фронтенде. Подробности файлов — в HANDOFF.md, раздел 3.

- `main.py` — точка входа (Procfile), не трогать без необходимости.
- `routes_whynot.py` — вся актуальная REST API, самый живой файл.
- `bot.py` — Telegram-бот; новые Postgres-хендлеры вперемешку со старыми
  sqlite-хендлерами легаси-версии — новый код добавлять в постгрес-секцию
  (внизу файла, там же где `/bind`, приём файлов, просрочки).
- `db/models.py` — модели + `_MIGRATIONS` (список идемпотентных ALTER
  TABLE, выполняется при каждом старте).
- `api.py` — FastAPI-обвязка, `/health`, легаси sqlite API (не развивать).

## Как вносить изменения в схему БД

Нет Alembic в реальности (хотя пакет в requirements). Новую колонку —
добавлять и в класс модели, и отдельной строкой
`"ALTER TABLE x ADD COLUMN IF NOT EXISTS y TYPE"` в `_MIGRATIONS` в
`db/models.py`. Список выполняется целиком при каждом старте процесса,
каждая строка обёрнута в try/except — одна неудачная миграция не роняет
остальные. Никогда не редактировать старые строки в этом списке (они уже
выполнились в проде) — только дописывать новые в конец.

Новый статус/роль (текстовые поля, не Postgres enum) — просто добавить
строку в соответствующий Python-set (`USER_ROLES`, `TASK_STATUSES` в
`routes_whynot.py`), миграция не нужна.

## Деплой и проверка

Нет CI, нет тестов. Стандартный цикл: правишь код → `git push` в `main` →
Railway передеплоивает сам (1-3 минуты) → проверяешь:

```bash
curl -s https://worker-production-7137.up.railway.app/health
curl -s https://worker-production-7137.up.railway.app/api/bot-status
```

`/health` → `{"db":"ok", ...}` подтверждает, что новые колонки/таблицы из
`_MIGRATIONS` реально появились (сравнивай счётчики до/после). Если меняешь
фронтенд (`webapp/index.html` или `sw.js`) — **обязательно бампни версию
кэша** в `webapp/sw.js` (`const CACHE = "whynot-os-vN"`), иначе у
пользователей Service Worker будет годами отдавать старую версию из кэша.

## Частые грабли

- **Сервис `postgres` в Railway — без видимого volume. Не перезапускать,
  не редеплоить и не менять его переменные**, пока не выяснено, где лежат
  данные, и не сделан `pg_dump` — иначе можно потерять всю боевую базу
  (HANDOFF.md, раздел 10).
- **`DATABASE_URL` — единственный источник адреса и пароля базы.** В коде
  дефолта нет и не должно быть (репозиторий публичный): без переменной
  приложение падает при старте. Пароль БД сменён в октябре 2026, у worker
  `DATABASE_URL` — готовая строка, при смене пароля обновлять вручную.
  Никаких секретов в код и в эти .md-файлы.
- **Не поднимать `api.py` отдельно с `RUN_BOT=1`, если `main.py` уже
  запущен** — два одновременных `getUpdates` на один токен бота дают
  409-конфликт с Telegram.
- **Уведомления через Telegram — best-effort, без ретраев и без сигнала
  об ошибке.** Если жалуются «не пришло уведомление» — первым делом
  проверить, жал ли получатель Start в личке с ботом (иначе Telegram
  физически не даёт боту написать первым).
- **1 клиент ≈ 1 проект** — так исторически сложилось в UI (раньше можно
  было создавать несколько проектов на клиента, убрали как путающее).
  Не удивляйся, если в модели данных ещё остались следы многопроектности.
- Если правишь `routes_whynot.py`, ищи готовые хелперы перед тем как
  писать новые: `_notify_project`, `_tg_send`, `_telegram_id_for`,
  `_log_status` (история статусов/таймлайн), `_can_edit_content`
  (кто может редактировать контент), `_my_project_ids` (фильтр «мои
  проекты» для AM/директора).
